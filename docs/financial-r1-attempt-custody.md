# R1 first-attempt custody

The retained R1 module owns an unnumbered, unregistered append-only attempt leaf. It stores the original business key `(kind, organizationId, reference)`, four role refs, full canonical command and its byte digest, scope, writer epoch and recorded time. `FINANCIAL_R1_ATTEMPT_DDL` does not register or apply a migration.

`buildFinancialR1AttemptCustodyStatement` returns a fixed claim with thirteen returned columns. Existing business/role claims or C0/R1 history suppress a new claim. The row cannot be replaced, updated or deleted. `buildFinancialR1ClaimedCoPreparationBatch` embeds exact original-claim equality in the Financial registration/R1 original/mandatory-receipt predicates. Its terminal mandatory CHECK rolls back all five statements if that claim is missing or crossed. The C0 pair is unchanged.

The existing `buildFinancialR1AttemptCustodyStatement` entry point now uses `buildFinancialR1BoundedAttemptCustodyStatement`. Its sixteen semantic inputs retain all original claim predicates and the exact thirteen-column postimage. Equal-looking values from different namespaces keep distinct slots. The compiler maps the fixed legacy predicate positions and refuses a mismatched mapping before execution. It changes SQL parameter placement only; it does not accept caller SQL or add an authority callback. Local compatibility checks keep the 100-variable and 100-expression-depth ceilings: the exact forty-five Root predicate inputs plus the claim fit in sixty-one variables. A separate local Miniflare D1 regression now executes the sixteen-bind claim through the explicit D1 acknowledgement adapter and Money writer. Remote D1 and positive genuine Root admission remain separately unqualified.

Both builders return SQL DATA; neither executes a write nor authorizes NEW, payer admission or first dispatch. An actual issuer must select the original once from its genuine request/source, obtain its own first claim changes1 plus exact thirteen-column postimage and original read, then proceed only in that same acknowledged invocation with its allNEW and same-primary currentness guards. The qualified prepare/current-consent methods remain unavailable; the older unclaimed DATA compiler is not an authorized issuer.

`createFinancialR1AttemptDataReader(options)` has query-only original-full-command and stable-business-key historical reads. A committed claim survives later preparation rollback and can be read after reopening storage. Pending, not-found or unknown is never permission to retry, select current terms, change key/family or resume. An initial unknown claim plus no observed row remains unknown: a claim that never committed provides no durable negative fence. Authoritative original custody and ordered terminal/read evidence remain the actual issuer/transport responsibility.

Root Auth/RP registration and Financial action/C0 registration are distinct namespaces. A historical record, matching DTO, fresh facade or in-memory latch cannot replace genuine credential and separate human binding, source currentness, qualified Clock or final allNEW acceptance/firstdispatch CAS. No payment/consent/challenge/proof wire changes.

Local tests use actual Money S for claim writes and inject response loss after a real local commit, then close/reopen the SQLite file in the same process. Full-five fixtures retain the existing isolated raw-R permit frame: the current C0 compiler directly references reserved Money tables that public S rejects. These fixtures are neither native D1 nor a mounted authorized pipeline. Schema activation is separate.

## Request-owned original selection for RP presentation

`createFinancialActionConsentR1Reader(originalConnection, actualRequest, selectedWorkspaceId).readRetainedActionConsentR1(challengeRef)` uses the actual Root request registration, static port/context assertion, credential original and distinct human binding. It connects the request-owned entry to `readFinancialRequestBoundR1History` and returns the exact stored R1 original, action identity, UTF-8 terms, billing binding, action source, realm/scope, canonical full command, and the validated R1/C0 mandatory receipt refs. The final selected Org owner/membership plus Root source, credential class and Principal predicates are checked in one primary SELECT; original connection/port/context/query identity is rechecked across awaits. Credential-row Org/Workspace and selected payment scope remain separate. No plan/body/terms reconstruction, disclosure-ref alias, callback qualifier or caller credential/Clock/SQL is accepted.

This reader supplies historical selected originals that RP may present; it does not prove that the exact bytes were displayed or affirmatively accepted, mint consent, or authorize NEW/current payer/first dispatch. The RP-facing entry refuses absent/partial/unknown history as unavailable. The original historical GET remains separate and never grants retry/rekey/resume. The DATA-only store's same-named unavailable method is intentional because that store has no original request connection. A route/mount, the genuine R1 issuing producer, native source qualification, actual RP display/consent custody and allNEW same-primary command CAS remain separate implementation work.

Within one request-owned reader, the first GET lazily starts exactly one Root capture. Parallel and later GETs share those original opaque handles; null, rejection or an initially invalid origin stays unavailable rather than triggering another observer. Only the capture Promise is retained. Every GET revalidates the original handles and re-reads Financial originals, receipts, selected owner and source predicates; a previous found result is never cached. A SQL unknown can recover by historical GET with that same held capture. The held observation is not a new observedAt, acceptedAt, consent permission or current-admission clock claim.

`readFinancialActionConsentR1RequestCaptures(originalConnection, actualRequest, selectedWorkspaceId, exactReader, exactReturnedOriginal)` returns the **same** Root capture object used for that successful read. Its private origin record is installed only after the fresh Financial/receipt/currentness read succeeds. Every argument must match by identity or exact workspace string; copies, proxies, inherited results and a different reader or Request are unavailable. The static reader reasserts the original Root registration, port/context, query and reader methods, then validates the actual credential and distinct human handles against the selected scope. It performs no observer, SQL, Clock sample or write and accepts no caller-provided captures.

The returned captures establish historical origin only. An old successful result can still supply its original handles after a later SQL failure; that does not assert fresh currentness, consent or permission. RP must validate those same handles with Root's static assertions, sample its qualified request Clock once, and use the same originals with the final same-primary currentness/consent predicates. A later R1 GET still executes fresh SQL and can refuse. This is per-reader singleflight only; creating a new reader is not a durable continuation or retry permit. The standalone historical function retains its per-invocation observation behavior.

## Existing Accounts proof projection

`readFinancialActionConsentR1IdentityEvidenceData(connection, request, workspaceId, exactReader, exactR1Original, originalProofRequest, loaded, current)` joins DATA from the existing Accounts proof ABI. It first asserts the same successful R1/capture origin, then detaches the original three-field proof request and both complete `found`/`current` responses. The requested proof reference must match both identical whole proof projections. All ten challenge fields, including the original action fingerprint, must equal retained C0. Proof issuer/client/subject/**sid** must match the actual Root RP identity. Accounts' private `issuerSessionId` remains separate from OIDC `sid`; neither it nor identity generation is derived from RP metadata.

The returned frozen `financial-proof` candidate contains the original proof reference, challenge registration, identity generation and four parent pins in Accounts' fixed grant/issuerSession/client/accountGeneration order. It does not synthesize a Control event pin from a genesis snapshot. Missing, unknown, not-current, crossed or malformed data is unavailable; there is no `not-required` fallback. The function performs no RPC, SQL, Clock sample, observer or write, and does not change the R1 result, consent wire or digest recipe.

Matching input DTOs can pass this DATA join. It is not an Accounts reader-origin assertion, current-consent verifier or NEW grant. The owning request composition must capture the actual Accounts reader and original proof request before its RPCs, retain unknown original-reference recovery and verify the actual source/current proof. Root retains genuine request/source composition, fc9 retains the Accounts/RP proof and explicit-consent/current-verifier connection, and Financial retains allNEW same-primary acceptance and first-dispatch CAS. Local tests use real Financial R1/SQLite with synthetic external Root and Accounts data; they do not qualify that actual RPC/mount, native D1, explicit consent or business E2E.

## Local D1 claim regression

`tests/shared-financial-r1-bounded-claim-d1.test.ts` copies the existing synthetic fixture schema and seed rows into an isolated Miniflare D1 instance, then runs the actual bounded claim and original reader with the same native session, verified test realm and Money wrapper. It covers all five action kinds, the exact thirteen-column postimage, unchanged and changed-business replays, query-only recovery after a committed batch acknowledgement is lost, and freeze/epoch refusal. A positive native claim image and a named late constraint distinguish the rollback case from an earlier failure; the failed batch leaves no claim or Money permit.

This is local D1 execution of SQL DATA, with synthetic external Stripe/realm inputs. It does not execute the five-statement R1/C0 preparation, establish a genuine Root request, admit NEW, or authorize a Stripe request. The test deliberately submits replay SQL to check immutability; the historical reader itself performs no retry or write.
